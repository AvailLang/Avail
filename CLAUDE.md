## Build and Test Commands

The repo holds several independent Gradle builds, each with its own `gradlew`
wrapper (`avail/`, `avail-artifact/`, `avail-stdlib/`, `avail-server/`,
`avail-cli/`, `gradle-plugin/`). There is no top-level `gradlew`. The main VM
and Anvil IDE live in `avail/`, so the commands below run from inside that
directory (or use `avail/gradlew -p avail <task>` from the repo root).

```bash
# Build
./gradlew build

# Run all tests (needs 4–6 GB heap; configured automatically)
./gradlew test

# Run a single test class
./gradlew test --tests "avail.test.ArithmeticTest"

# Build the Anvil IDE fat JAR
./gradlew package

# Build and launch Anvil
./gradlew packageAndRun

# Assemble a self-contained Anvil.app on macOS (jpackage + jlinked JDK)
./gradlew packageApp

# Same, then open the .app
./gradlew packageAppAndRun

# Regenerate bootstrap files (needed after adding primitives or special objects)
./gradlew generateAllNames

# Generate API docs
./gradlew dokkaGeneratePublicationHtml
```

JDK toolchain is Java 26 (Oracle vendor); Kotlin/Java emit Java 25 bytecode
because Kotlin 2.3.10 cannot yet target 26. Tests run headless
(`java.awt.headless=true`).

`packageApp` is macOS-only. It writes `avail/build/jpackage/Anvil.app`, a
self-contained bundle whose `Contents/runtime` is a jlinked image of the
toolchain JDK. The launcher and runtime are single-architecture: build on
an x86_64 host to get an x86_64 bundle, on Apple Silicon to get arm64.

## Repository Layout

This is a multi-project Gradle build. The main module is `avail/`. Supporting subprojects:

| Module | Purpose |
|---|---|
| `avail/` | VM, compiler, optimizer, and Anvil IDE |
| `avail-artifact/` | Artifact packaging utilities |
| `avail-stdlib/` | Standard library packaging |
| `avail-cli/` | Command-line launcher |
| `avail-server/` | HTTP/WebSocket server |
| `gradle-plugin/` | Gradle plugin for building Avail projects |

Avail source modules live in `avail/distro/src/avail/`. Compiled module caches are stored in `.repo` directories alongside their source roots.

## Core Architecture

### The Descriptor/Object Pattern

Every Avail value is an `AvailObject`. Its behavior is entirely delegated to a companion `Descriptor` instance stored in the object's `descriptor` field. Descriptors are shared across all instances of the same type/mutability.

- `AbstractDescriptor` (~131 KB) — declares every operation an object can perform, with default implementations that throw `UnsupportedOperationException`.
- `Descriptor` extends `AbstractDescriptor` with helpers.
- `IndirectionDescriptor` — replaces a mutable object's descriptor to forward all operations to a target object (used for hash-consing and forwarding after mutation).
- Mutability is tracked as `MUTABLE`, `IMMUTABLE`, or `SHARED`. Calling `makeImmutable()` / `makeShared()` swaps the descriptor to a read-only variant.
- Typed interfaces (`A_Atom`, `A_Function`, `A_Tuple`, etc. in `descriptor/*/`) define the public API for each concept. `AvailObject` implements all of them by dispatching to its descriptor.

`AvailObjectRepresentation` (the superclass of `AvailObject`) holds the raw slot storage: integer slots (`long[]`) and object slots (`AvailObject[]`). Slot layout is declared by enum classes annotated with `@IntegerSlotsEnum` / `@ObjectSlotsEnum`.

### Two-Level Execution

**L1 (portable bytecode):** Stack-based, generated by the compiler, stored in `RawFunction` objects. Defined in `interpreter/levelOne/`. Human-readable via `L1Disassembler` / `L1Decompiler`.

**L2 (optimized IR):** Register-based, produced by the optimizer from L1. Lives in `L2Chunk` objects. The `interpreter/levelTwo/` package contains the instruction set, operand types, and register allocator. `L2SimpleChunk` is a lightweight non-JIT path; `L2JVMChunk` compiles to JVM bytecode via ASM.

The optimizer pipeline lives in `optimizer/`. It performs type propagation, inlining, and specialization before emitting L2 or JVM bytecode.

**Calling convention:** A successful call returns an `AvailObject`. A call that needs to reify the stack returns `null` and sets `Interpreter.currentReifier`. Primitives have typed subclasses (`Primitive0`…`Primitive4`, `PrimitiveN`) with `attempt0()`…`attemptN()` methods to avoid argument list allocation at L2 call sites.

### Fibers and Continuations

Avail concurrency is fiber-based (not OS threads). `A_Fiber` objects are scheduled by `AvailRuntime` onto a thread pool. A fiber's call stack is represented as a chain of `A_Continuation` objects (snapshots of stack frames). Suspension captures the continuation; resumption restores it.

`Interpreter` is the per-thread execution engine. It runs chunks, dispatches primitives, and handles reification. `AvailRuntime` owns the fiber queue, module registry, and method table.

### Module and Method System

Methods are identified by `A_Atom` names. Each method holds a set of `A_Definition` objects (each with a function and a type signature). Dispatch is performed at call time by `LookupTree` in `dispatch/`, which builds a decision tree from the type signatures.

The compiler resolves method sends during compilation when possible, embedding type restrictions. `SemanticRestriction`s let library authors refine return types at compile time.

Module loading is managed by `AvailBuilder` in `builder/`. Modules declare `Uses`, `Extends`, and `Names`. The module root system (configured via `availRoots` system property) maps logical module names to filesystem locations.

### Anvil IDE

`anvil/AvailWorkbench.kt` is the main IDE window. Key sub-systems:
- `anvil/text/` — `CodePane` (styled editor), `TextLineNumber`, editor kits
- `anvil/debugger/` — `AvailDebugger` breakpoint/step UI
- `anvil/actions/` — Swing actions for workbench commands
- `anvil/manager/` — Project manager window

The IDE uses **FlatLaf** for the look and feel (`FlatDarkLaf` / `FlatLightLaf` selected from `AvailProjectManagerRunner` based on `AvailWorkbench.darkMode`).

All UI mutations must happen on the EDT. The codebase uses `SwingUtilities.isEventDispatchThread()` assertions liberally to enforce this.

## Key Conventions

- **Avail object protocols** are interfaces prefixed with `A_` (e.g., `A_Tuple`, `A_Function`). Add new operations there first, then implement in the relevant descriptor(s) and provide a default `unsupported` implementation in `AbstractDescriptor`.
- **Slot enums** use `@IntegerSlotsEnum` / `@ObjectSlotsEnum` annotations and are nested inside their descriptor class.
- **Primitive naming**: `P_<ConceptName>` in `interpreter/primitive/<category>/`.
- **Bootstrap**: Adding a primitive or special object requires running `generateAllNames` to regenerate the `.properties` files consumed by the Avail bootstrap modules.
- **L2 operations**: New L2 ops go in `interpreter/levelTwo/operation/`, implementing `L2Operation`. Register types and read/write semantics must be declared precisely for the register allocator.
